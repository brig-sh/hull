1. Sandbox Architecture: TrustedBSD, Seatbelt, SBPL

The macOS sandbox (commonly called Seatbelt) is built on the TrustedBSD Mandatory Access Control (MAC) framework ported into XNU. It operates through a layered kernel architecture:

  1. Sandbox.kext -- a kernel extension that registers itself as a MAC policy module. It is consulted whenever a sandboxed process executes a monitored system call. A single denial from any policy module cancels the syscall and returns an error.
  2. libsandbox -- a userspace library that compiles sandbox profiles. It contains a custom Scheme interpreter based on TinySCHEME that evaluates SBPL (Sandbox Profile Language) source into opaque bytecode passed to Sandbox.kext for enforcement.
  3. sandbox-exec -- a CLI wrapper that reads an SBPL profile, compiles it via libsandbox, and applies it to a child process before exec. This is the only documented way to apply Seatbelt policies to arbitrary user-space processes without App Store enrollment or Xcode entitlements.
  4. sandbox_init() -- the C API that processes can call to sandbox themselves. Chromium, Firefox, and other applications use this to self-confine child processes.

The compilation pipeline: SBPL source + parameters (entitlements, paths, bundle IDs) are evaluated by the TinySCHEME interpreter in libsandbox, producing a binary profile that is passed through the kernel to Sandbox.kext. The last applicable rule in a profile determines the final sandbox decision.

Sources: Ubrigens -- A Whirlwind Tour of the Apple Sandbox, David Nesting -- SBPL Reference, Chromium -- The Mac Sandbox

2. SBPL Language Reference

SBPL is an S-expression (Scheme-dialect) language. Profiles consist of (allow ...) and (deny ...) rules with operations and optional filters.

Core Syntax

(version 1)
(deny default)                              ; deny everything by default

(allow file-read* (subpath "/usr/lib"))     ; allow reading under /usr/lib
(allow file-read* (literal "/dev/null"))    ; exact path match
(deny  network-outbound)                    ; block all outbound network
(allow process-exec (literal "/bin/sh"))    ; allow executing /bin/sh
(allow mach-lookup (global-name "com.apple.system.logger"))

3. Apple's Own System Sandbox Profiles

Apple extensively uses sandbox profiles for its own system daemons. Profiles are stored in two locations:

  • /System/Library/Sandbox/Profiles/*.sb -- system daemon profiles
  • /usr/share/sandbox/*.sb -- additional profiles

Key System Profiles

  • application.sb -- the base profile for App Store applications. It dynamically generates rules based on supplied entitlements and parameters. This is what backs the "App Sandbox" feature.
  • bsd.sb -- base profile providing standard POSIX/BSD functionality. Other profiles can (import) it as a base layer.
  • rootless.conf -- the platform_profile profile that implements SIP (System Integrity Protection), which is conceptually a sandbox profile applied system-wide.

Most Apple daemon services run in a Service Sandbox context, applying their sandbox via sandbox_init_XXX() in their main() function. This gives each daemon the minimum required permissions for its functionality.

Note: On modern macOS, many of these profiles are compiled into the shared cache and are not directly readable as plaintext .sb files. Security researchers have created tools like simbple (an SBPL interpreter) and SandBlaster to reverse-engineer compiled profiles.
Sources: HackTricks -- macOS Sandbox, Ubrigens -- Sandbox Tour, SandBlaster: Reversing the Apple Sandbox

4. Chromium/Chrome macOS Sandbox

Chromium is the most sophisticated public user of the macOS Seatbelt sandbox. It uses the sandbox(7) API (not the App Sandbox) to confine child processes.

Architecture

  • Sandbox profiles are written in SBPL and stored as .sb files in the source tree.
  • Different process types receive different sandbox configurations: content/common/common.sb for shared setup, content/renderer/renderer.sb for renderer/extension processes, etc.
  • The --process-type argument designates which sandbox each subprocess receives.
  • Profiles are compiled via Seatbelt::Compile into binary representations, transmitted through Mojo IPC to new processes via SeatbeltExecClient, then applied by SeatbeltExecServer::ApplySandboxProfile.

V2 Sandbox Design (Current)

  • Removes the historically unsandboxed "warmup phase" -- processes are sandboxed from the start.
  • All process types use V2 except the GPU process (still on V1).
  • Default-deny posture: (deny default) with explicit allowlists for file access, Mach services, sysctls, IPC, IOKit calls.
  • Processes may access system libraries and frameworks but require explicit allowlists for everything else.

Runtime Parameters

SBPL profiles accept parameters not known at compile time, passed at process launch:

  • Sandbox logging flags
  • Home directory path
  • OS version info
  • App bundle location
  • Process PID
  • Permitted read/write directories

Development Workflow

Developers use --enable-sandbox-logging to empirically identify required resources, then for each denied resource they choose: grant access, implement brokering (controlled proxy access), or fix the code to eliminate the need.

Key insight: Chromium demonstrates that SBPL profiles can be compiled and transmitted programmatically via sandbox_init_with_parameters() -- you do not need to use sandbox-exec at all. The C API is what production applications use.
Sources: Chromium -- Mac Sandbox V2 Design Doc, Chromium -- The Mac Sandbox README, Chromium -- sandbox_mac.h

5. Firefox macOS Sandbox

Firefox also uses the macOS Seatbelt sandbox, applying a whitelist (default-deny) policy to all sandboxed process types.

Content Process Sandbox Levels

Mac content processes use sandbox level 3 (the most restrictive). Levels control progressive filesystem restriction:

LevelFilesystem Access
Level 1Global file read permitted
Level 2Blocks ~/Library and profile directory (except /extensions and /chrome)
Level 3No global read access; only /extensions and /chrome within the profile directory

What the Content Sandbox Allows

  • File reads: System paths (/System, /usr/lib, /Library/GPUBundles), app bundle, /dev/random, /dev/urandom, /dev/null, /dev/zero, timezone data, fonts
  • Mach services: com.apple.windowserver.active (conditional), com.apple.system.opendirectoryd.libinfo, com.apple.CoreServices.coreservicesd, com.apple.audio.coreaudiod, com.apple.cvmsServ (GPU acceleration)
  • File writes: Only to debug directories when debugWriteDir is defined
  • Network: Not explicitly allowed (denied by default)
  • IPC: POSIX shared memory for specific prefixes (CFPBS:, AudioIO)

Runtime Parameters

The policy uses parameterization: SHOULD_LOG, SANDBOX_LEVEL_1/2/3, MAC_OS_VERSION, APP_PATH, PROFILE_DIR, HOME_PATH, and testing paths.

Debugging

Enable violation logging via security.sandbox.logging.enabled=true pref or MOZ_SANDBOX_LOGGING environment variable. Violations appear in Console.app.

Sources: Mozilla Wiki -- Security/Sandbox, Firefox Source -- SandboxPolicyContent.h, Mozilla Wiki -- macOS Sandbox Release

6. Docker Desktop and Container Runtimes on macOS

Docker Desktop on macOS does not use sandbox-exec for isolation. Instead, it runs a full Linux VM.

Docker Desktop Architecture

  • Docker's Virtual Machine Monitor (VMM) uses Apple's Hypervisor.framework to run a Linux VM natively.
  • All Linux containers run inside this VM, which provides kernel-level isolation from macOS.
  • As of February 2026, QEMU-based virtualization is being deprecated in Docker Desktop for Mac in favor of Hypervisor.framework exclusively.

Docker Sandboxes (New in 2026)

Docker Desktop 4.58+ introduced "Sandboxes" -- each sandbox wraps a container in a lightweight microVM using Apple Virtualization Framework on macOS:

  • Each sandbox gets its own Linux kernel (hardware-boundary isolation)
  • Private Docker daemon inside the VM
  • Full docker build, run, and compose with no socket mounting and no host privileges
  • Sub-second start times through optimized kernel configuration
Key takeaway: Docker on macOS relies on VM-level isolation (Hypervisor.framework / Virtualization.framework), not process-level sandboxing. The VM boundary is the security boundary.

Other macOS Container Projects

  • OSXIEC -- a native macOS container solution that works without virtualization or disabling SIP. Provides VLAN networking and vulnerability scanning, but isolation is "less robust compared to Linux-based containers."
  • Darwin Containers -- attempts to port Docker functionality to macOS but requires disabling SIP, recommended only for development.
Sources: Docker Blog -- Why MicroVMs, Medium -- Containerization on macOS vs Linux, Docker Blog -- QEMU Deprecation

7. Apple Containerization Framework

Announced at WWDC 2025, Apple's Containerization is a Swift framework and container CLI for running Linux containers on macOS.

Architecture

  • One-VM-per-container model -- each OCI Linux container runs inside its own lightweight VM via Virtualization.framework on Apple Silicon.
  • Sub-second start times through optimized Linux kernel configuration and minimal root filesystem.
  • OCI-compatible: pull/push images from any standard container registry.
  • Each container gets a dedicated IP address (no port forwarding needed).
  • APIs to create and populate ext4 filesystems and interact with Netlink sockets.

Timeline

  • v0.1.0 at WWDC 2025 (June 2025)
  • v0.8.0 in January 2026
  • v1.0.0 on June 9, 2026
  • Requires macOS 26 (Tahoe)
  • 30K+ GitHub stars, 840+ forks as of June 2026
Important distinction: Apple Containerization is strictly for Linux containers running inside VMs -- it is not a replacement for sandbox-exec for native macOS process isolation. It does not provide Seatbelt-style sandboxing of native macOS processes.
Sources: GitHub -- apple/containerization, GitHub -- apple/container (CLI), Medium -- Apple Container 0.8.0, The New Stack -- Apple Container Framework

8. Open-Source Projects Using sandbox-exec for Isolation

SandVault Active

Two-layer isolation for AI coding agents on macOS:

  • Layer 1: Limited user account (sandvault-$USER) with standard privileges
  • Layer 2: sandbox-exec restricting filesystem to /Users/Shared/sv-$USER and system directories
  • Supports Claude Code, OpenAI Codex, OpenCode, Google Gemini
  • Includes browser automation (Chrome DevTools Protocol) and iOS Simulator integration
  • Documents that "macOS does not support nested sandboxes" and provides -x/--no-sandbox flag for workaround
GitHub -- webcoyote/sandvault

bx-mac Active

File-level sandboxing tool that dynamically generates sandbox-exec profiles:

  • Scans $HOME at launch, generates per-directory deny rules
  • Works around SBPL quirk: deny rules always override allow rules regardless of order. Never denies parent directories of allowed paths.
  • Supports .bxignore files with rw: and ro: prefixes for granular access
  • Protects .ssh, .gnupg, .docker, ~/Documents, ~/Desktop, ~/Downloads, password managers
  • Detects nested sandbox conflicts, auto-adds --no-sandbox for Electron apps
  • Does NOT restrict network access or provide process isolation beyond filesystem
GitHub -- holtwick/bx-mac

Microsoft MXC (eXecution Containers) Experimental

Policy-driven, layered isolation with a Seatbelt backend for macOS:

  • Generates TinyScheme SBPL profiles dynamically and applies via sandbox_init() in pre_exec
  • Supports readwritePaths, readonlyPaths, deniedPaths, and network policies
  • Display isolation: denies mach-lookup for WindowServer services
  • Clipboard isolation: denies com.apple.pasteboard.1
  • Input isolation: denies iokit-open for IOHIDLibUserClient
  • Limitation: Cannot interpose at TLS layer; per-host network filtering is best-effort (DNS not resolved by Seatbelt)

GitHub -- microsoft/mxc seatbelt-backend.md

Alcoholless Active

Lightweight sandbox using user-account isolation instead of sandbox-exec:

  • Creates isolated user accounts (alcless_${USER}_default) using su, sudo, rsync
  • Syncs working directory to isolated user, runs command, syncs back
  • No performance overhead (no virtualization), direct hardware access (GPU)
  • Compatible with GitHub Actions (no nested virtualization needed)
  • Deliberately avoids sandbox-exec due to deprecation concerns
Medium (NTT Labs) -- Alcoholless

Ozymandias42/macOS-Sandbox-Profiles

Collection of custom sandbox-exec profiles for various applications.

GitHub -- Ozymandias42/macOS-Sandbox-Profiles

ai-jail

Sandbox for AI agents that uses bubblewrap on Linux and sandbox-exec on macOS as fallback.

GitHub -- akitaonrails/ai-jail

9. Sandboxing Build Tools and Untrusted Code

Bazel (darwin-sandbox)

Bazel is the most prominent production user of sandbox-exec for build isolation:

  • Each build action runs inside sandbox-exec, confined to its execroot/ directory
  • Prevents actions from reading undeclared input files or writing unexpected outputs
  • The darwin-sandbox strategy "uses Apple's sandbox-exec tool to achieve roughly the same as the Linux sandbox"
  • Critical limitation: Cannot run sandbox-exec inside an already-sandboxed process; Bazel falls back to processwrapper-sandbox in that case
Bazel -- Sandboxing Documentation

macOSSandboxBuild

Provides profiles for building open-source software (configure, make, cmake) in a sandbox:

  • Four profiles: confined.sb (no network), download.sb (network allowed), nomach.sb (blocks Mach lookups), ping.sb (restrictive, ping only)
  • Parameterized paths: _RX1 (read/execute source), _RW1 (read/write build output), _TMPDIR (temp files)
  • Denies execution of suid programs, blocks sysctl access, restricts reads to unauthorized directories
# Example: sandboxed cmake build
sandbox-exec -D_RX1="/path/to/source" \
             -D_RW1="/path/to/build" \
             -D_TMPDIR="/tmp/build" \
             -f confined.sb \
             cmake --build /path/to/build
GitHub -- BrianSwift/macOSSandboxBuild

Example: Restrictive Profile for Untrusted Code

(version 1)
(deny default)

; Allow basic process execution
(allow process-fork)
(allow process-exec (literal "/usr/bin/clang"))
(allow process-exec (literal "/usr/bin/clang++"))

; Read-only access to system libraries and headers
(allow file-read* (subpath "/usr/lib"))
(allow file-read* (subpath "/usr/include"))
(allow file-read* (subpath "/Library/Developer/CommandLineTools"))

; Read/write only the build directory
(allow file-read* file-write* (subpath "/tmp/sandbox-build"))

; Block all network access (deny default handles this)
; Block access to home directory (deny default handles this)
; Block Mach service lookups except essentials
(allow mach-lookup (global-name "com.apple.system.logger"))

10. Nesting and Composing Sandbox Profiles

Sandbox profiles CANNOT be nested. Attempting to run sandbox-exec inside a process that is already sandboxed results in "sandbox_apply: Operation not permitted". This is a hard kernel limitation.

Impact on Real-World Tools

  • Bazel: Falls back to processwrapper-sandbox when already inside a sandbox
  • SandVault: Provides -x/--no-sandbox flag; tools like swift and xcodebuild that already use sandbox-exec internally will fail inside SandVault's sandbox
  • bx-mac: Detects existing sandbox via CODEBOX_SANDBOX=1 env var and EPERM probes; refuses to start if nested
  • Electron apps: Already sandboxed internally; require --no-sandbox flag when run inside an outer sandbox

Profile Composition (Partial Alternative)

While nesting is impossible, profiles can be composed at the SBPL level using (import):

(version 1)
(import "/System/Library/Sandbox/Profiles/bsd.sb")  ; base layer
(deny network-outbound)                               ; additional restriction
(deny file-write* (subpath "/Users"))                  ; further restriction

This is compile-time composition only -- you cannot layer on additional restrictions to an already-running sandboxed process.

Sources: jmmv.dev -- A quick glance at macOS' sandbox-exec, GitHub -- SandVault, GitHub -- bx-mac, Bazel -- Sandboxing

12. Practical Limitations of macOS Sandbox for Container-Like Isolation

  1. No filesystem virtualization. Only path-level allow/deny rules. Cannot create isolated mount points, overlayfs, or bind mounts. A sandboxed process sees the full filesystem tree; it just gets EPERM on denied paths.
  2. No PID isolation. Sandboxed processes share the global PID namespace. A sandboxed process can see all other processes via ps (unless process-info* is denied).
  3. No network namespace. Cannot create separate network stacks or virtual interfaces. Network filtering is limited to allow/deny outbound/inbound with best-effort host matching (no DNS resolution).
  4. No resource limits. No CPU, memory, or I/O caps. No cgroup equivalent.
  5. Cannot nest. Kernel hard limitation. Tools that internally sandbox (Xcode, Swift compiler, Electron, Bazel) will fail inside an outer sandbox.
  6. Deny overrides allow. In SBPL, deny rules always take precedence regardless of order. This makes "allow everything except X" straightforward but "deny everything except fine-grained allows" tricky -- you cannot override a deny with a more specific allow.
  7. No TLS interposition. Cannot inspect or filter HTTPS traffic. Per-host network filtering is best-effort at the TCP connect level.
  8. GPU/Display cannot be restricted. Metal and Cocoa are system-level; sandbox-exec cannot meaningfully restrict GPU or display access.
  9. Undocumented profile language. SBPL is an "Apple System Private Interface" with no official documentation. Changes between macOS versions can break profiles.
  10. Static at launch. The sandbox profile is applied once at process start. Cannot add or remove restrictions dynamically (except via sandbox extensions for specific file access grants).
  11. SIP overrides profiles. System Integrity Protection takes precedence over sandbox rules for protected paths.
  12. Deprecated with no replacement. Apple recommends "App Sandbox" (requires Xcode, code signing, entitlements), which does not cover CLI/server process sandboxing use cases.

13. Deprecation Status and Future

Current State (June 2026)

  • sandbox-exec has been marked DEPRECATED in its man page since at least 2016-2017.
  • The deprecation warning says: "Consider adopting the App Sandbox instead."
  • Despite the deprecation, sandbox-exec remains present and functional on macOS 26 (Tahoe).
  • The underlying sandbox subsystem is actively maintained -- it is what all of Apple's system software uses for sandboxing.
  • Apple has provided no official deprecation timeline and no documented migration path for CLI/server process sandboxing.

Why App Sandbox Is Not a Replacement

  • Requires com.apple.security.app-sandbox entitlement and code signing
  • Designed for GUI apps distributed through the Mac App Store
  • Not suitable for headless server processes, build tools, or arbitrary CLI commands
  • Cannot be applied to third-party or unsigned binaries

Alternative Paths

ApproachViability
Continue using sandbox-execWorks today. Risk of future removal, but unlikely given Apple's own dependency on the subsystem.
Use sandbox_init() C API directlyWhat Chromium/Firefox do. More stable than the CLI wrapper. Also technically private API.
Apple Containerization frameworkLinux VMs only. Not for native macOS process isolation.
User-account isolation (Alcoholless)No API deprecation risk. Coarser isolation. No filesystem virtualization.
VM-based isolation (Docker, Vz)Strongest isolation. Higher overhead. Overkill for lightweight process sandboxing.

Open Issue on Apple's Repo

Issue #737 on the Apple Containerization repo asks three specific questions: (1) Will Apple remove sandbox-exec? (2) Is there a supported API for applying Seatbelt policies to unsigned binaries? (3) Will Apple Containerization support lightweight process isolation without a Linux VM? As of June 2026, Apple has not responded.

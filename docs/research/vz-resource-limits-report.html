2. Dynamic Reconfiguration

Can CPU/memory be changed after VM creation? No

cpuCount and memorySize are set at configuration time and are immutable once the VZVirtualMachine is instantiated. There is no API to change them while the VM is running, paused, or in any other state. No hot-add, no hot-remove. WWDC 2026 (session 224) introduced USB passthrough, custom Virtio devices, DiskImageKit, and advanced networking but no dynamic CPU/memory reconfiguration.

Memory Balloon Device (Partial Dynamic Memory)

The one runtime memory adjustment mechanism: VZVirtioTraditionalMemoryBalloonDeviceConfiguration implements the standard Virtio memory balloon protocol. The host can request the guest to inflate (free memory back to host) or deflate (reclaim memory). This does NOT change memorySize -- it changes how much of the fixed allocation the guest actively uses.

Sources: Apple Docs -- VZVirtioTraditionalMemoryBalloonDevice, WWDC 2026 Session 224

4. Network Isolation

Attachment Types

TypeSinceLayerEntitlementIsolation
VZNATNetworkDeviceAttachment macOS 12 L3 (NAT) Base only Partial -- vmnet isolation enabled but ARP spoofing possible
VZBridgedNetworkDeviceAttachment macOS 12 L2 (bridge) com.apple.vm.networking None -- same broadcast domain as host LAN
VZFileHandleNetworkDeviceAttachment macOS 11 L2 (raw frames) Base only Best -- all packets flow through userspace daemon

Can you limit network bandwidth per VM? No

Virtualization.framework exposes no bandwidth limiting or traffic shaping APIs. No per-VM throttling on any attachment type.

Workarounds for bandwidth control:

  • VZFileHandleNetworkDeviceAttachment + custom daemon: Implement token-bucket rate limiting on the raw packet stream
  • macOS pf / dnctl / dummynet: Host-level packet filter rules on vmnet bridge interfaces (e.g., bridge100)
  • Guest-level tc/netem: Traffic control inside the guest Linux kernel

VZNATNetworkDeviceAttachment Details

  • Uses vmnet.framework internally in shared mode
  • Creates virtual bridge bridge100 on host
  • Default subnet: 192.168.64.0/24 (gateway 192.168.64.1)
  • vmnet_enable_isolation_key enabled automatically (not configurable via VZ API)
  • No root/sudo required

VZFileHandleNetworkDeviceAttachment Details

  • Operates at data link layer -- raw Ethernet frames via connected datagram socket
  • Each send(2)/recv(2) = one Ethernet frame
  • Configurable MTU (default 1500)
  • Can connect to: vmnet, custom daemons (softnet), userspace stacks (gvisor-tap-vsock)
  • This is the approach used by Cirrus Labs' Tart for production multi-tenant isolation
ARP spoofing risk with NAT: While vmnet_enable_isolation_key provides bridge-level isolation, it does NOT prevent ARP spoofing. Any VM can answer ARP requests with its own MAC and divert other VMs' traffic. For multi-tenant deployments, use VZFileHandleNetworkDeviceAttachment with a filtering daemon like softnet.

Softnet -- Production Network Isolation

Used by Cirrus Labs (Tart) and forked by OpenAI. A Rust-based userspace packet filter implementing:

  • DHCP snooping: only DHCP traffic initially allowed; learns each VM's assigned IP
  • Source IP filtering: after DHCP, only allows packets from VM's assigned IP
  • Destination filtering: only globally routable IPs and vmnet gateway
  • ARP spoofing prevention by construction
Sources: Apple Docs -- VZNATNetworkDeviceAttachment, Apple Docs -- VZFileHandleNetworkDeviceAttachment, Cirrus Labs -- Isolating Network Between Tart VMs, softnet (Cirrus Labs), softnet (OpenAI fork)

Can you limit disk I/O per VM? No

Virtualization.framework exposes no IOPS or bandwidth limits, no I/O scheduling priority or weight, no per-VM disk quotas.

Workarounds for I/O containment:

  • Guest-level cgroups: Linux blkio controller for IOPS/bandwidth limits inside guest
  • NBD attachment: VZNetworkBlockDeviceStorageDeviceAttachment with a custom NBD server implementing throttling
  • Fixed-size images: Pre-sized RAW disk images bound guest storage by image size

VZDiskImageStorageDeviceAttachment Options

Caching Modes (VZDiskImageCachingMode, macOS 12+):

ModeBehavior
.automaticFramework decides (often = cached)
.uncachedNo host-side caching; each I/O goes to disk
.cachedAggressive host-side caching
EXT4 corruption risk: .automatic/.cached modes have been reported to cause EXT4 filesystem corruption in Linux guests under heavy I/O with VZVirtioBlockDeviceConfiguration. Use .uncached with virtio block, or switch to VZNVMExpressControllerDeviceConfiguration (macOS 14+).

Synchronization Modes (VZDiskImageSynchronizationMode, macOS 12+):

ModeBehavior
.fullAll flush/barrier commands forwarded to host. Maximum integrity.
.fsyncBest-effort sync (fsync only, no barriers). Middle ground.
.noneNo sync. Best perf, no crash safety.

Virtiofs (VZVirtioFileSystemDeviceConfiguration)

  • Configuration: tag (mount identifier) + share (directory share)
  • VZSharedDirectory: url + readOnly boolean
  • No throughput controls whatsoever -- operates via direct memory-mapped I/O
  • Near-native host filesystem performance
  • Isolation depends entirely on host process configuring distinct paths per VM
Sources: Apple Docs -- VZDiskImageStorageDeviceAttachment, Apple Docs -- VZDiskBlockDeviceStorageDeviceAttachment, Apple Docs -- VZVirtioFileSystemDeviceConfiguration, UTM PR #5869 -- NVMe caching fix

6. Hypervisor.framework & Kernel Isolation

Architecture

Yes, Virtualization.framework uses Hypervisor.framework underneath.

  • Hypervisor.framework (macOS 10.10, 2014): Low-level C API for hardware virtualization primitives -- vCPU creation/execution, memory mapping, register access. "Roughly equivalent to KVM."
  • Virtualization.framework (macOS 11, 2020): High-level Swift/ObjC API built on top. Adds Virtio device backends, boot loaders, configuration APIs.
  • The kernel hypervisor code lives in XNU's closed-source hypervisor subsystem under hv_vm_* / hv_vcpu_* functions.

ARM64 Isolation Mechanisms

On Apple Silicon, the hypervisor operates at Exception Level 2 (EL2) using VHE (Virtualization Host Extensions):

Stage-2 Address Translation (hardware memory isolation):

  • ARM provides two-stage address translation: Stage 1 (guest VA to guest IPA, controlled by guest at EL1) and Stage 2 (IPA to host PA, controlled by hypervisor at EL2)
  • Stage-2 page table entries include: valid bits, access flags, permission bits (RW/RO), execute-never (XN), 4KB page alignment
  • Each VM gets hardware-enforced memory isolation -- guest cannot access any physical memory not explicitly mapped by the hypervisor
  • Architecturally equivalent to Intel EPT (Extended Page Tables)

Register and instruction trapping:

  • Privileged EL1 register accesses trapped to EL2 for emulation
  • Fine-grained register trapping via HFGRTR_EL2/HFGWTR_EL2
  • SME/SVE registers: unbanked registers (Z, P, ZA, ZT0) require state spilling on traps
  • Virtual interrupt forwarding to specific VMs/vCPUs

VHE mode exclusively: Apple Silicon runs the host kernel at EL2 (not classic EL1+EL2 split). Guest kernels run at EL1. This is VHE (Virtualization Host Extensions) -- the host uses EL2 privileges directly, with no separate hypervisor binary.

VM limit: macOS enforces a limit of 2 concurrent macOS guest VMs via hv_apple_isa_vm_quota in the kernel. A boot arg exists to change this but is gated behind CSR_ALLOW_APPLE_INTERNAL on release builds. Linux guest VMs are not subject to this limit.
Sources: vmfunc.re -- Reverse Engineering ARM64 Hypervisor Internals, Eclectic Light -- Hypervisors and Virtualisation, Eclectic Light -- Virtualisation is Different (2026), XNU SME Documentation, Khronokernel -- Beating the 2 VM Limit

Isolation equivalence: At the hardware level, Apple and KVM use the same ARM isolation mechanisms (EL2, stage-2 page tables). The isolation guarantee comes from the silicon, not the software. The difference is in software attack surface (VMM complexity, device emulation).

9. Gaps Summary for hullX

Capabilities that enterprise hypervisors provide but Virtualization.framework does not:

CapabilityStatusWorkaround
Network bandwidth limitMissingVZFileHandleNetworkDeviceAttachment + softnet/custom daemon
Disk I/O throttle (IOPS/BW)MissingGuest cgroups blkio, or NBD attachment with custom server
CPU hot-add/removeMissingNone -- must recreate VM
Memory hot-add/removeMissingMemory balloon (adjusts usage within fixed allocation)
CPU affinity/pinningMissingNone
CPU scheduling priorityMissingNone -- all vCPUs are high-QoS
Per-VM disk quotaMissingFixed-size RAW images, or host-level APFS volume limits
Network inter-VM isolationPartialsoftnet via VZFileHandleNetworkDeviceAttachment
Storage inter-VM isolationPartialCorrect host-side path configuration (no framework enforcement)
Bottom line: Virtualization.framework provides strong hardware-level isolation (stage-2 page tables, entitlement-gated access) but minimal resource management. You get a flat CPU count and memory size, both immutable after VM creation. Everything else -- bandwidth limits, I/O throttling, scheduling priority, inter-VM network isolation -- must be implemented in userspace or inside the guest. The NBD storage attachment and VZFileHandleNetworkDeviceAttachment are the primary extension points for building custom resource controls.

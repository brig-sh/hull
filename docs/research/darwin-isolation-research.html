macOS/Darwin Process Isolation Primitives

Technical research report -- June 2026 | 15 sources, 5 search angles, adversarially verified

Executive Summary: XNU provides zero Linux-style namespaces (no mount, PID, network, user, UTS, or IPC namespaces) and no cgroups. The strongest non-VM isolation primitive is sandbox-exec (Seatbelt/MACF), which provides capability-based access control over ~300 operation types but cannot create private namespaces. Apple's own containerization framework (WWDC 2025) chose one-VM-per-container via Virtualization.framework, confirming the gap. The Darwin persona mechanism provides partial UID remapping but requires a private entitlement. chroot exists but is blocked by AMFI when SIP is enabled.

1. chroot on macOS Broken by default

Does it work?

The chroot(2) syscall exists on macOS but is effectively blocked by AMFI (Apple Mobile File Integrity) when SIP is enabled. Attempting to execute binaries inside a chroot produces:

AMFI: hook..execve() hardened runtime not allowed in chroot
AMFI: hook..execve() killing pid 93189: not allowed in chroot

The process is killed with SIGKILL (signal 9).

Source: threedots.ovh -- chroot on modern macOS

Requirements and Limitations

  • Root required: Always. The chroot(2) syscall is privileged (section 8 man page).
  • SIP must be disabled for any macOS-signed binary to execute inside the chroot. AMFI, which enforces hardened runtime restrictions, blocks execution otherwise.
  • Alternative: The boot argument amfi_get_out_of_my_way=1 can bypass AMFI enforcement without fully disabling SIP.
  • ~21 GB of bindings needed: macOS binaries depend on libSystem.B.dylib and system frameworks. You need bindfs (via macFUSE) to bind /bin, /usr/lib, /usr/libexec, /System, /Library into the chroot since macOS lacks native bind mounts.
  • Read-only root FS: Since Big Sur, the system volume is a Signed System Volume. Chroots must be in writable locations (~/ or external volumes).
  • Not real isolation: chroot only changes the filesystem root path. Processes can escape via fchdir() to pre-opened file descriptors outside the chroot. No PID, network, IPC, or resource isolation.

Sources: eddieh gist, macos-jail

2. sandbox-exec / Seatbelt Deprecated but functional

Key takeaway: This is the strongest non-VM isolation primitive on macOS. It does not require root, works with SIP enabled, is inherited by children, and cannot be escaped. However, it provides access control (allow/deny), NOT namespace isolation (private views).

Architecture

  • Built on the TrustedBSD Mandatory Access Control Framework (MACF). The Sandbox kernel extension hooks ~300 policy checkpoints throughout XNU.
  • Profiles are written in SBPL (Sandbox Profile Language), a Scheme dialect interpreted by TinyScheme within libsandbox. Profiles are compiled to bytecode containing filter and action instructions.
  • Does NOT require root. Any user can sandbox their own processes.
  • Irrevocable: Once applied, the sandbox can only be tightened, never loosened or removed.
  • Inherited by children: All child processes inherit the parent's sandbox.
  • Violations return EPERM to the calling process.

Source: bdash.net.nz -- Sandboxing on macOS

Profile Example

(version 1)
(deny default)                                    ; deny everything
(allow file-read* (subpath "/usr/lib"))            ; allow reading system libs
(allow file-read* (subpath "/usr/share"))
(allow process-exec (literal "/usr/bin/python3"))  ; allow executing python
(allow network* (local ip "localhost:*"))           ; localhost only
(deny network-outbound (remote ip "*:*"))          ; block all outbound

C API

  • Predefined profiles: kSBXProfileNoInternet, kSBXProfileNoNetwork, kSBXProfileNoWrite, kSBXProfileNoWriteExceptTemporary, kSBXProfilePureComputation
  • Lower-level: sandbox_compile_string() + sandbox_apply()
  • Extensions: sandbox_extension_issue_file(), sandbox_extension_consume() -- for granting temporary access tokens
  • Chromium pattern (gold standard): Parent compiles SBPL profile, sends compiled bytecode to child via pipe, child applies it to itself before running main()

Sources: bdash.net.nz, Chromium sandbox design

Deprecation Status

sandbox-exec(1) is marked DEPRECATED in its man page (since ~macOS 10.13). However, it still works on macOS 26.x. The underlying Sandbox.kext is essential to macOS and cannot be removed. macOS ships 501 sandbox profiles in /System/Library/Sandbox/Profiles/. There is no replacement for CLI/server process sandboxing.

Source: apple/containerization issue #737

3. Namespace-Like Mechanisms on XNU None exist

Bottom line: XNU has zero Linux-style namespaces. No mount namespaces, no PID namespaces, no network namespaces, no user namespaces, no UTS namespaces, no IPC namespaces. FreeBSD jails were never ported to Darwin.

Mount Namespaces

Not available. XNU maintains a single global mount table: extern TAILQ_HEAD(mntlist, mount) mountlist; in mount_internal.h. There are no per-process mount visibility fields in struct mount. No MNT_* flags relate to namespace isolation.

Source: darwin-xnu mount_internal.h

PID Namespaces

Not available. The BSD process table is flat and global. struct proc in proc_internal.h has no namespace or container ID fields. Every process has a globally unique PID.

Source: XNU proc_internal.h

Network Namespaces

Not available. There is no per-process network stack. The vmnet framework provides virtual networking for VMs but operates at the VM level. Seatbelt can restrict network access (allow/deny) but cannot create separate network stacks.

Source: containerd Discussion #5525

User Namespaces

Not available. No UID remapping mechanism exists. The persona subsystem (see section 5) provides limited identity switching but not Linux-style user namespace mapping.

FreeBSD Jails

Not ported. Despite XNU's BSD heritage: "Darwin doesn't include the jail() syscall, nor zones."

Source: darwin-dev mailing list

Source: darwin-xnu spawn.h, posixspawn README

Isolation-Relevant Private Attribute Setters

Resource Isolation

  • posix_spawnattr_set_qos_clamp_np(attr, qos) -- Caps max QoS class. Values: NONE, UTILITY, BACKGROUND, MAINTENANCE. Limits CPU scheduling priority, not access to resources.
  • posix_spawnattr_setjetsam_ext(attr, flags, priority, memlimit_active, memlimit_inactive) -- Sets jetsam (OOM-killer) attributes. Memory limits in MB. Flags include JETSAM_MEMLIMIT_ACTIVE_FATAL (0x04) and JETSAM_MEMLIMIT_INACTIVE_FATAL (0x08).
  • posix_spawnattr_setcpumonitor(attr, percent, interval) -- CPU usage monitoring threshold.
  • posix_spawnattr_setpcontrol_np(attr, pcontrol) -- Resource starvation behavior: NONE, THROTTLE, SUSPEND, KILL.
  • posix_spawnattr_set_darwin_role_np(attr, role) -- Process role for scheduling.

Identity Isolation

  • psa_persona_info field -- Spawn with a different persona (UID/GID/groups). Flags: POSIX_SPAWN_PERSONA_FLAGS_OVERRIDE (0x1), POSIX_SPAWN_PERSONA_FLAGS_VERIFY (0x2).
  • psa_posix_cred_info field -- Set POSIX credentials (UID, GID, groups, login). Flags: POSIX_SPAWN_POSIX_CRED_UID (0x00010000), etc.
  • responsibility_spawnattrs_setdisclaim(attr, 1) -- Decouples TCC responsibility from parent. Child becomes its own "responsible process" for permission dialogs.

Security-Adjacent (Private/Undocumented)

  • posix_spawnattr_setmacpolicyinfo_np(attr, "policy_name", data, datalen) -- Attaches opaque MAC policy data for TrustedBSD hooks during spawn. The Sandbox.kext is one such MAC policy. This is how launch constraints work internally.
  • posix_spawnattr_set_platform_np(attr, PLATFORM_IOS, 0) -- Run as iOS process on Apple Silicon, which changes sandbox initialization behavior.
  • posix_spawnattr_set_subsystem_root_path_np(attr, path) -- Sets subsystem root path (possibly for relocated subsystem roots; exact semantics unclear).

Sources: spawn_internal.h, CVE-2025-43253, Mickey's Blog

Can you set a sandbox profile via posix_spawn? No. Apple DTS explicitly states: "We don't support custom sandboxes at all." Child processes inherit the parent's sandbox. The child must apply its own sandbox after launch via sandbox_init_with_parameters() or sandbox_compile_string() / sandbox_apply(). The Chromium pattern (compile in parent, send bytecode via pipe, child applies before main) is the gold standard.

Source: Apple Developer Forums, Chromium sandbox design

5. Darwin Persona Mechanism Partial UID isolation

The persona mechanism is a kernel-level identity abstraction that allows processes to adopt alternate user identities (UID, GID, groups, login name). It provides partial UID namespace-like isolation but requires the private entitlement com.apple.private.persona-mgmt.

Syscall Interface

Single multiplexed syscall #494 (SYS_persona) with NO_SYSCALL_STUB (no libSystem wrapper):

494 AUE_PERSONA ALL { int persona(uint32_t operation, uint32_t flags,
    struct kpersona_info *info, uid_t *id, size_t *idlen, char *path)
    NO_SYSCALL_STUB; }

Operations

PERSONA_OP_ALLOC0Allocate persona (no path)
PERSONA_OP_PALLOC1Allocate persona with filesystem path
PERSONA_OP_DEALLOC2Deallocate persona
PERSONA_OP_GET3Get current thread's persona ID
PERSONA_OP_INFO4Get persona info by ID
PERSONA_OP_PIDINFO5Get persona info for a PID
PERSONA_OP_FIND6Find persona by name/UID
PERSONA_OP_GETPATH7Get filesystem path for persona
PERSONA_OP_FIND_BY_TYPE8Find personas by type

Persona Types

TypeValuePurpose
PERSONA_GUEST1Guest/temporary sessions
PERSONA_MANAGED2MDM-managed sessions
PERSONA_PRIV3Privileged persona
PERSONA_SYSTEM4System processes (adoption NOT allowed)
PERSONA_DEFAULT5Default/primary user
PERSONA_SYSTEM_PROXY6System proxy (adoption NOT allowed)
PERSONA_SYS_EXT7System extensions
PERSONA_ENTERPRISE8Enterprise/managed

Kernel Implementation Details

  • Global list all_personas; max 512 personas (MAX_PERSONAS)
  • IDs start at 501 (FIRST_PERSONA_ID), increment by 10 (PERSONA_ID_STEP)
  • PERSONA_MAGIC = 0x0aa55aa0
  • During persona_proc_adopt(), the kernel calls kauth_cred_proc_update() with a credential derivation callback that creates new credentials from the persona's UID/GID/groups
  • The P_ADOPTPERSONA flag is set on the process during adoption
  • RLIMIT_NPROC is enforced per-persona-UID

Can It Provide UID Namespace-Like Isolation?

Partially yes:

  • Assigns a process a different UID, GID, and group memberships at the kernel level
  • Each persona has a member process list tracking which processes belong to it
  • Resource limits are enforced per-persona-UID
  • Each persona can have an associated filesystem path

But NOT a full user namespace:

  • No UID remapping (no inner-to-outer UID mapping)
  • No filesystem ownership translation
  • The persona UID is a real system UID visible in file ownership and process tables
  • Max 512 personas is a hard kernel limit
  • Requires private entitlement com.apple.private.persona-mgmt

Real-World Usage

  • Shared iPad: Provisions per-user UNIX UIDs and APFS volumes using personas for multi-user session isolation
  • TrollStore exploit: Exploited com.apple.private.persona-mgmt to spawn root helpers from non-root processes. Patched in iOS 17.6/18.0

Sources: persona.h, kern_persona.c, Apple Shared iPad Security, TrollStore wiki

6. Process Groups and Sessions Signal scope only

setsid(2) and setpgid(2) exist on macOS and behave per POSIX.

  • setsid() creates a new session and process group
  • setpgid() joins or creates a process group within the current session
  • POSIX_SPAWN_SETSID (0x0400) flag creates a new session atomically at spawn time
Isolation is limited to signal delivery and job control. Process groups only scope kill(-pgid, sig) targeting and terminal foreground/background status. They provide no filesystem, network, PID namespace, or resource isolation. There are no hidden isolation properties beyond POSIX.

Source: Apple setsid(2) man page

7. Private Mount Trees Not possible

  • No mount namespaces: Linux unshare(CLONE_NEWNS) has no equivalent. All processes see the single global mount table.
  • No native bind mounts: macOS does not provide mount --bind. Workaround: bindfs via macFUSE.
  • No union/overlay mounts: "macOS does not support stacking in its file-system design." APFS does not support overlayfs.
  • Firmlinks are NOT a namespace mechanism: They merge APFS System + Data volumes into a unified hierarchy (introduced in Catalina). They are system-wide, immutable, and the same for every process. Users cannot create OS-level firmlinks; only synthetic firmlinks via /etc/synthetic.conf.
  • APFS clonefile(2) is the practical alternative: instant COW copies of directory trees. Not a mount namespace, but provides copy-on-write filesystem copies per instance.
  • Sparse bundle disk images are another workaround: create a .sparseimage, mount it, use it as an isolated filesystem root.

Sources: containerd #5525, Eclectic Light -- firmlinks

8. Mach Port Namespaces Per-task by default

This is the one area where macOS actually has genuine namespace isolation:

  • Each task has its own isolated port namespace. Port names (32-bit integers) are meaningful only within the owning task. Sending a port name integer to another task does NOT grant access.
  • Capability-based security: Port rights are unforgeable capabilities. The only way to obtain a right: (1) create it yourself, or (2) receive it from another task via Mach IPC message.
  • Receive rights are exclusive: Only one task holds the receive right (MPSC queue). Prevents message interception.
  • Port rights are NOT inherited across fork/exec except for special ports (task port, bootstrap port, host port, exception ports).
  • Seatbelt can restrict mach-lookup operations, preventing service discovery and connection.
Weakness: The bootstrap port leaks service discovery. Any process can look up Mach services by name through launchd's bootstrap server, unless restricted by sandbox mach-lookup rules.

Sources: Darling -- Mach Ports, Apple Kernel Programming Guide

10. SIP / Rootless Interactions Protection, not isolation

SIP is NOT a container isolation mechanism. It protects system integrity but does not provide per-process isolation boundaries.

What SIP Does

  • Blocks task_for_pid() on protected processes
  • Prevents DTrace attachment to protected processes
  • Sanitizes DYLD_LIBRARY_PATH and LD_LIBRARY_PATH for system binaries
  • Prevents modifications to /System, /bin, /sbin, /usr (excluding /usr/local)
  • Enforces hardened runtime via AMFI

How SIP Affects Isolation Attempts

  • chroot: Blocked. AMFI kills processes attempting to exec hardened-runtime binaries inside a chroot.
  • sandbox-exec: Not affected. Works fine with SIP enabled.
  • Persona: The com.apple.private.persona-mgmt entitlement cannot be used by ad-hoc signed binaries when SIP+AMFI are active. Requires SIP disabled or amfi_get_out_of_my_way=1.
  • Private frameworks: Many private APIs for isolation require restricted entitlements that are only valid with SIP disabled.

11. Resource Limits (cgroups equivalent) No group hierarchy

  • No cgroups equivalent. No hierarchical resource controller for process groups.
  • POSIX rlimits only: setrlimit(2) provides per-process RLIMIT_CPU, RLIMIT_DATA, RLIMIT_FSIZE, RLIMIT_NOFILE (default 256, max 10240), etc.
  • XNU task policy subsystem (via task_policy_set() Mach trap): Task roles, QoS tiers (0-5), IO throttling, Darwin Background mode, App Nap suppression. Per-process only.
  • No memory cgroup equivalent: Cannot hard-limit a process group's memory and have the kernel OOM-kill within the group. RLIMIT_DATA only limits the data segment.
  • posix_spawn attributes can set jetsam limits (memory in MB, fatal/non-fatal) and QoS clamps at spawn time, but these are per-process.

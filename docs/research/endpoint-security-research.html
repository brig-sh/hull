1. Overview and Architecture

The Endpoint Security (ES) framework is Apple's C API for monitoring and controlling security-relevant system events on macOS. Introduced in macOS 10.15 Catalina (2019), it replaces the deprecated KAuth KPI, the unsupported MAC Kernel Framework, and the deprecated OpenBSM audit trail.

Architecture (4 components)
  1. EndpointSecurity.kext -- Kernel extension that hooks syscalls (execve, posix_spawn, open, etc.) and emits events
  2. /usr/libexec/endpointsecurityd -- User-space daemon that validates system extensions, manages client connections, handles installation/uninstallation, early boot registration
  3. libEndpointSecurity.dylib -- Developer-facing user-space library providing the public API for third-party ES clients
  4. libEndpointSecuritySystem.dylib -- Apple-internal library for system components to emit ES events (backgroundtaskmanagementd, XProtect, etc.)

Event flow: Kernel-emitted events originate from syscall hooks in EndpointSecurity.kext and are proxied through endpointsecurityd to subscribed ES clients. User-space events (authentication, XProtect, BTM) are emitted by Apple daemons via libEndpointSecuritySystem.dylib.

ES clients can be implemented as either standalone daemons (LaunchDaemons) or System Extensions. System Extensions benefit from SIP protection against tampering.

Sources: Red Canary mac-monitor wiki, MeekoLab ES Introduction

2. AUTH vs NOTIFY -- Active Enforcement vs Passive Monitoring

AUTH Events (Authorization)

  • Fire before the action occurs
  • The OS blocks the action until the ES client responds with ES_AUTH_RESULT_ALLOW or ES_AUTH_RESULT_DENY
  • Response must arrive before a deadline (system-defined, not configurable)
  • If deadline passes without response, the action is allowed by default
  • Use es_respond_auth_result() or es_respond_flags_result() (for AUTH_OPEN only)
  • Can actively block malicious execution, file modification, library loading, etc.

NOTIFY Events (Notification)

  • Fire after or during the action
  • No response required -- purely observational
  • Better for telemetry collection and behavioral analysis
  • Many more NOTIFY events than AUTH events (97 vs 44)
  • All AUTH events have a corresponding NOTIFY variant; many NOTIFY events have no AUTH counterpart

Sources: Alkenso -- Two Machine Debug of AUTH Events, Elastic -- Part 3

4. Monitoring Capabilities by Category

Process Lifecycle

Full visibility into process creation, execution, forking, exit, signaling, suspension, and task introspection.

  • AUTH: EXEC, SIGNAL, PROC_CHECK, PROC_SUSPEND_RESUME, GET_TASK, GET_TASK_READ
  • NOTIFY: EXEC, FORK, EXIT, TRACE, REMOTE_THREAD_CREATE, GET_TASK_NAME, GET_TASK_INSPECT, CS_INVALIDATED
  • Process events include: PID (via audit token), executable path, command-line arguments, environment variables, code signing info (signing ID, team ID, cdhash, platform binary flag), codesigning flags

File System Operations

Comprehensive coverage of file creation, modification, deletion, renaming, linking, metadata changes, extended attributes, and ACLs.

  • AUTH: OPEN, CREATE, RENAME, UNLINK, LINK, READLINK, TRUNCATE, CLONE, COPYFILE, EXCHANGEDATA, SETATTRLIST, SETEXTATTR, SETFLAGS, SETMODE, SETOWNER, SETACL, DELETEEXTATTR, GETATTRLIST, GETEXTATTR, LISTEXTATTR, READDIR, SEARCHFS, FSGETPATH
  • NOTIFY: All of the above plus WRITE, CLOSE, STAT, ACCESS, LOOKUP, DUP, FCNTL

Memory and Code Injection

Monitor and control memory mapping, protection changes, and task port access (used for process injection).

  • AUTH: MMAP, MPROTECT, GET_TASK, GET_TASK_READ
  • NOTIFY: MMAP, MPROTECT, GET_TASK, GET_TASK_READ, GET_TASK_INSPECT, GET_TASK_NAME, REMOTE_THREAD_CREATE

Mount/Unmount

  • AUTH: MOUNT, REMOUNT | NOTIFY: MOUNT, UNMOUNT, REMOUNT

Privilege and Identity Changes (NOTIFY only)

  • SETUID, SETGID, SETEUID, SETEGID, SETREUID, SETREGID, CHROOT, SU, SUDO

Authentication and Sessions (macOS 13+, NOTIFY only)

  • AUTHENTICATION (local login, Touch ID, Apple Watch unlock)
  • LW_SESSION_LOGIN/LOGOUT/LOCK/UNLOCK
  • OPENSSH_LOGIN/LOGOUT, LOGIN_LOGIN/LOGOUT
  • SCREENSHARING_ATTACH/DETACH
  • AUTHORIZATION_PETITION/JUDGEMENT (macOS 14+)

Open Directory (macOS 14+, NOTIFY only)

  • User/group creation, deletion, modification, password changes, attribute operations

Security and Gatekeeper (NOTIFY only)

  • XP_MALWARE_DETECTED, XP_MALWARE_REMEDIATED (macOS 13+)
  • GATEKEEPER_USER_OVERRIDE (macOS 15+)
  • TCC_MODIFY (macOS 15.4+)
  • CS_INVALIDATED (code signature invalidation)
  • PROFILE_ADD/REMOVE (macOS 14+)

IPC -- UNIX Domain Sockets Only

  • AUTH: UIPC_BIND, UIPC_CONNECT
  • NOTIFY: UIPC_BIND, UIPC_CONNECT, XPC_CONNECT (macOS 14+)
  • Note: These are UNIX-domain sockets only, not TCP/UDP network sockets

5. Network Monitoring: ES vs NetworkExtension

Critical Gap: ES Intentionally Excludes TCP/UDP Network Events

Apple explicitly stated at WWDC 2020:

"Those of you who have already worked with the EndpointSecurity framework have likely noticed that we do not provide events related to networking operations. This is intentional as these are better covered by the NetworkExtension framework."

What ES provides for IPC:

  • UIPC_BIND, UIPC_CONNECT -- UNIX domain socket operations only (AUTH + NOTIFY)
  • XPC_CONNECT -- XPC connection events (NOTIFY, macOS 14+)

What ES does NOT provide:

  • TCP/UDP connect, bind, listen, accept
  • DNS resolution
  • Remote IP/port information
  • Any packet-level inspection

Emerging change (macOS 26.4, undocumented): The LuLu firewall project has reverse-engineered ES_EVENT_TYPE_RESERVED_5 and RESERVED_6 as network connection AUTH/NOTIFY events, with a struct containing address family, resolved IP, hostname, and resolver path. These events carry a 15-second AUTH deadline. This would be a significant shift from Apple's prior stance.

For network monitoring today, use NetworkExtension with a Content Filter provider. Both ES and NetworkExtension can coexist in a single System Extension.

Sources: Apple Developer Forums -- ES and network events, Objective-See -- Building a Firewall via ES, WWDC 2020 -- Build an ES app

6. Mach Messages, XPC, and IPC Monitoring

Mach message monitoring is NOT supported by EndpointSecurity. There are no event types for raw Mach message send/receive.

What IS available:

  • NOTIFY_XPC_CONNECT (macOS 14+) -- notifies when an XPC connection is established, but not message content
  • AUTH_UIPC_BIND / AUTH_UIPC_CONNECT -- for UNIX domain sockets used for IPC
  • AUTH_GET_TASK / AUTH_GET_TASK_READ -- can block task port access, which is the prerequisite for Mach-based process injection
  • IOKit open events for device-level IPC monitoring

For Mach-level monitoring, one would historically have needed kernel instrumentation (now deprecated with KEXT). There is no current user-space API that provides visibility into individual Mach message send/receive operations.

8. System Extensions vs Kernel Extensions

AspectKernel Extensions (KEXT)System Extensions (SYSEXT)
Execution contextKernel space (ring 0)User space
StatusDeprecated since macOS 10.15; blocked on Apple Silicon without explicit user overrideCurrent recommended approach
Crash impactFull kernel panicProcess crash only; OS continues
SIP protectionNoYes (rootless protection against tampering)
FrameworksKAuth KPI, MAC frameworkEndpointSecurity, NetworkExtension, DriverKit
DistributionNotarization + user approvalNotarization + user approval + MDM for enterprise silent install
Apple SiliconRequires reduced security boot + explicit user actionWorks at full security level

The transition timeline: Apple announced KEXT deprecation at WWDC 2019, introduced System Extensions in macOS 10.15.4, and has progressively restricted KEXT loading. On Apple Silicon Macs, loading a KEXT requires booting into Recovery, lowering security policy, and explicitly allowing the extension -- making KEXTs impractical for most production use.

9. Entitlements and Requirements

Required Entitlement

<key>com.apple.developer.endpoint-security.client</key>
<true/>

This entitlement must be granted by Apple through the System Extension Request Form. Without it, es_new_client() returns ES_NEW_CLIENT_RESULT_ERR_NOT_ENTITLED.

Full Requirements

  1. Apple-granted entitlement: com.apple.developer.endpoint-security.client -- requires application to Apple, approval for your team ID
  2. Provisioning profile: Must create a provisioning profile that includes the entitlement via Apple Developer Account; Xcode imports it into the project
  3. Code signing: Must be properly code-signed (Hardened Runtime enabled)
  4. Root execution: The ES client process must run as root (UID 0)
  5. Full Disk Access: Must be granted TCC Full Disk Access authorization (either via System Preferences or MDM)
  6. Libraries to link: libEndpointSecurity.tbd, libbsm.tbd

Development / Testing Workarounds

  • Disable SIP to bypass entitlement check (for development only)
  • Apple's eslogger CLI tool (macOS 13+) ships pre-entitled and can output NOTIFY events as JSON without building a custom client
  • Red Canary's Mac Monitor provides a GUI for reading ES events without the formal entitlement

Internal Entitlement (Apple-only)

com.apple.private.endpoint-security.submit -- used by Apple daemons to emit events into the ES subsystem. Not available to third parties.

Sources: Apple -- ES client entitlement, Omar-Ikram ES demo, MeekoLab

10. Container Workload Monitoring and Isolation

Can ES Monitor Container-Like Workloads?

Yes, with caveats. EndpointSecurity operates at the system level and sees all processes on the host, regardless of whether they run inside a VM, a sandbox, or a container-like construct. For your hull use case (Virtualization.framework VMs and QEMU+HVF VMs):

  • Host-side process monitoring: ES can observe the VM hypervisor process itself (qemu, vz-runner), its file access patterns, mount operations, and any child processes it spawns on the host
  • Guest-side visibility: ES has no visibility into guest OS operations. It monitors the host kernel only. Processes running inside a Linux VM (the unikernel workload) are invisible to ES
  • Virtio/virtiofs file access: When the guest accesses shared host directories (via virtiofs or 9pfs), those accesses may generate file events on the host attributable to the VM process
  • Network: VM network traffic via vmnet-shared appears to the host as network activity of the hypervisor process; ES has no visibility into this (network events not supported), but NetworkExtension could observe it

Can ES Enforce Isolation?

Partially. AUTH events can block specific operations, but ES is not a sandbox mechanism:

  • AUTH_EXEC can prevent unauthorized binaries from executing
  • AUTH_OPEN/CREATE/UNLINK can restrict file access
  • AUTH_MOUNT/REMOUNT can prevent filesystem mounts
  • AUTH_MMAP/MPROTECT can restrict memory operations
  • But: ES has no concept of "containers" or per-process policy profiles. You would need to build the policy logic yourself, filtering by PID/audit token/path of the monitored process
  • Better alternatives for isolation: macOS Sandbox (Seatbelt) profiles via sandbox-exec (deprecated but functional), or Apple's Containerization framework

sandbox-exec vs ES for Container Isolation

An open issue in Apple's containerization repo highlights the tension: sandbox-exec (Seatbelt) remains the only documented way to apply declarative sandbox profiles to arbitrary processes without App Store enrollment, but it is deprecated with no formal removal timeline. ES provides observation and authorization callbacks but not declarative per-process sandbox profiles.

For hull, a combined approach could work: use ES AUTH events to monitor and gate host-side operations performed by the hypervisor process, while relying on the VM boundary itself for guest isolation.

11. Limitations

  1. No TCP/UDP network events (until possibly macOS 26.4; must use NetworkExtension)
  2. No Mach message monitoring -- cannot observe raw Mach IPC
  3. No guest VM visibility -- only monitors the host kernel, not guest OS
  4. Entitlement gatekeeping -- requires Apple approval, creating a barrier for small developers and open-source projects
  5. AUTH event deadline -- responses must arrive within a system-defined (non-configurable) deadline; slow handlers get killed
  6. No blocking in handler -- performing blocking operations in the ES callback will cause the system to kill the client when event volume is high
  7. Root required -- ES clients must run as UID 0
  8. No per-process policy profiles -- unlike Sandbox (Seatbelt), ES does not provide declarative per-process containment
  9. Compliance gap -- prevention-first architecture does not naturally log failed events as required by DISA/NIST standards
  10. No DNS event support -- DNS resolution is not observable through ES
  11. TCC events limited -- TCC_MODIFY only fires on grant/revoke, not for entitled binaries or when TCC silently denies
  12. Muting complexity -- high-volume events (STAT, ACCESS, LOOKUP) require careful muting to avoid performance degradation

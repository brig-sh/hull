1. TrustedBSD MAC Framework Overview

The Mandatory Access Control Framework (MACF) is the foundational security substrate in the XNU kernel, derived from the TrustedBSD project originally developed for FreeBSD. Unlike Discretionary Access Control (DAC) which governs traditional Unix file permissions, MAC enforces policies that users cannot alter.

The MACF itself makes no security decisions -- it is a stub layer that intercepts kernel operations and delegates decisions to registered Policy Modules. Multiple policies can be loaded simultaneously; results are composed with deny-wins semantics (all policies must approve for an operation to succeed).

Initialization (Three-Phase Boot Sequence)

  1. mac_policy_init() -- Pre-malloc phase. Initializes the mac_policy_list array, creates the mac_policy_mtx mutex.
  2. mac_policy_initmach() -- Post-Mach, pre-BSD phase. Calls load_security_extensions_function() which iterates over all kernel extensions with AppleSecurityExtension = true in their Info.plist. Sets mac_late = 1.
  3. mac_policy_initbsd() -- BSD phase. Creates audit data zone, calls mpo_policy_initbsd callback for all loaded policies.

Policy Registration

A policy module calls mac_policy_register(&my_policy_conf, &my_handle), typically from a KEXT start routine. The key structure:

struct mac_policy_conf {
    .mpc_name           // Short policy name (unique identifier)
    .mpc_fullname       // Human-readable full name
    .mpc_labelnames     // Array of label namespace names
    .mpc_labelname_count
    .mpc_ops            // Pointer to mac_policy_ops (callback table)
    .mpc_loadtime_flags // MPC_LOADTIME_FLAG_*
    .mpc_field_off      // Label slot offset storage
    .mpc_runtime_flags  // Set by framework
};

Loadtime Flags

FlagMeaning
MPC_LOADTIME_FLAG_UNLOADOKPermits policy unloading
MPC_LOADTIME_FLAG_NOTLATEMust load early in boot; late-load rejected
MPC_LOADTIME_FLAG_LABELMBUFSPolicy requires network buffer (mbuf) labeling

Policy Composition

When multiple policies are loaded, all must approve for an operation to succeed. Error precedence: EDEADLK > EINVAL > ESRCH > EACCES > EPERM.

3. MAC Hooks and Check Points

The MAC framework provides 300+ entry points in the mac_policy_ops structure. Hooks follow the naming convention:

  • Kernel-side: mac_<OBJECT>_<OPTYPE>_<OPNAME>()
  • Policy callbacks: mpo_<OBJECT>_<OPTYPE>_<OPNAME>()

Where OBJECT = cred, file, proc, vnode, socket, pipe, mount, devfs, mbuf, ifnet, iokit, system, etc. OPTYPE = check (access decision), label (lifecycle), notify (post-op).

Key Hook Categories

CategoryExample Hooks

File/Vnodempo_vnode_check_exec, mpo_vnode_check_open, mpo_vnode_check_read, mpo_vnode_check_write, mpo_vnode_check_signature
Mount/FSmpo_mount_check_mount, mpo_mount_check_umount, mpo_mount_check_getattr

Librarympo_file_check_library_validation, mpo_proc_check_run_cs_invalid
Systemmpo_policy_syscall (handles __mac_syscall from userspace)

Syscall Interception Flow

  1. User-space app initiates a syscall (e.g., open())
  2. Trap transitions to kernel mode (EL0 to EL1 on ARM64)
  3. MACF hooks execute before core kernel logic
  4. Registered callbacks execute sequentially across all loaded policies
  5. Results composed: all policies must approve (deny-wins)

4. Can Custom MAC Policies Be Loaded?

Effectively Blocked on Modern macOS

On modern macOS (especially Apple Silicon), custom MAC policy loading is effectively blocked for third parties. The MAC framework remains internal Apple infrastructure.

Via Kexts -- Theoretically Yes, Practically Blocked

The mac_policy.h header carries a prominent warning: "MAC policy is not KPI, see Technical Q&A QA1574, this header will be removed in next version."

macOS VersionMACF Kext Status
≤ 10.12 (Sierra)Full SDK support, kexts load freely
10.13 (High Sierra)MAC headers removed from SDK; kexts still load via older SDK
10.15 (Catalina)Kext KPIs officially deprecated; System Extensions introduced
11 (Big Sur)Kexts using deprecated KPIs no longer load by default
Apple SiliconFull Security mode blocks all third-party kexts; Reduced Security required
15+ (Sequoia+)Continuing kext removal

Via System Extensions -- No

System Extensions run in userspace and have no access to the kernel's MAC framework. They cannot register MAC policies. They use higher-level frameworks: Endpoint Security, Network Extension, DriverKit.

Apple's Sanctioned Replacement: Endpoint Security Framework

EndpointSecurity.kext (Apple's own MAC policy module) proxies selected MAC events to userspace ES clients. The limitation: ES only exposes events Apple chooses to surface. Third parties cannot access undocumented system events.

5. AMFI (Apple Mobile File Integrity)

AMFI is a MAC Policy Module implemented as AppleMobileFileIntegrity.kext. It registers during mac_policy_initmach() through bootstrapLoadSecurityExtensions().

Three Components

ComponentLocationRole
Kernel Extension/System/Library/Extensions/AppleMobileFileIntegrity.kextRegisters MACF hooks, performs in-kernel enforcement
amfid daemon/usr/libexec/amfidFull code signature validation via Security.framework, certificate trust evaluation
IPCMach port HOST_AMFID_PORT (18)MIG subsystem, messages 1000-1008; response on reply port 1100

What AMFI Enforces

  • Code Signature Validation -- Two-stage: load-time CDHash check against Trust Caches (fast path), fallback to amfid for full validation. Runtime page-fault validation via cs_validate_page.
  • Entitlement Enforcement -- Validates that processes only use entitlements they are authorized to have.
  • Library Validation -- Platform binaries only load other platform binaries; loaded libraries must share TeamID.
  • Mach Task Port Protection -- Controls access via get-task-allow, task_for_pid-allow entitlements.
  • Memory Protection -- Prevents mapping executable memory for unsigned code.
  • Dyld Policy -- Blocks DYLD_INSERT_LIBRARIES injection for binaries with Hardened Runtime, Library Validation, CS_RESTRICT, or SUID/SGID bits.
  • Process Integrity -- Sets cs_hard | cs_kill flags at exec, killing process if code pages become invalid.

Trust Caches

On Apple Silicon, trust caches are part of the Secure Boot chain. They store precomputed CDHash values for Apple-signed binaries, enabling rapid validation without full cryptographic verification. Modern trust caches tie metadata to "launch constraints."

6. Code Signing, Entitlements, and AMFI Interaction

Restricted vs. Unrestricted Entitlements

TypeWho Can UseExamples
Unrestricted Any signed binary (including ad-hoc) com.apple.application-identifier, com.apple.security.application-groups.*, sandbox family
Restricted Apple-signed binaries, or binaries with Apple-approved provisioning profiles get-task-allow, com.apple.security.virtualization, com.apple.vm.networking, dynamic-codesigning, com.apple.security.cs.allow-jit
Critical for urunc-macos

The entitlements com.apple.security.virtualization and com.apple.vm.networking are restricted entitlements. AMFI will kill any ad-hoc signed binary claiming these -- unless SIP is disabled and amfi_get_out_of_my_way=1 is set.

AMFI Boot Arguments

Boot ArgEffectRequires SIP Off?
amfi_get_out_of_my_way=1Disables AMFI enforcement (restricted entitlements honored with ad-hoc signing)Yes
amfi_allow_any_signatureAllows any code signatureYes
amfi_unrestrict_task_for_pidAllows task_for_pid without entitlementsYes
cs_enforcement_disableSystem-wide code signing enforcement disableYes

AMFI and SIP Interaction

  • SIP protects AMFI's infrastructure -- prevents root from hijacking HOST_AMFID_PORT; only launchd can obtain special ports.
  • SIP gates AMFI boot arguments -- all AMFI-weakening boot args are ignored when SIP is enabled.
  • Layered enforcement: SIP enabled + AMFI enabled = maximum security. SIP off + amfi_get_out_of_my_way=1 = restricted entitlements work with ad-hoc signatures.

Dyld Policy Syscall

Bit 1: AMFI_DYLD_OUTPUT_ALLOW_PATH_VARS
Bit 2: AMFI_DYLD_OUTPUT_ALLOW_CUSTOM_SHARED_CACHE
Bit 3: AMFI_DYLD_OUTPUT_ALLOW_FALLBACK_PATHS
Bit 4: AMFI_DYLD_OUTPUT_ALLOW_PRINT_VARS
Bit 5: AMFI_DYLD_OUTPUT_ALLOW_FAILED_LIBRARY_INSERTION

7. cgroups Equivalent on macOS

No Equivalent Exists

macOS has no direct equivalent to Linux cgroups. There is no hierarchical, per-group resource accounting and limiting subsystem. Resource limits are fundamentally per-process (or per-UID for some limits like RLIMIT_NPROC).

macOS uses a collection of separate, per-process mechanisms:

  • setrlimit/getrlimit -- BSD resource limits
  • taskpolicy / process_policy -- XNU kernel task policy system
  • Jetsam / memorystatus -- memory pressure killing
  • launchd plist resource keys -- daemon resource configuration
  • QoS classes -- scheduling tiers
  • sandbox-exec profiles -- access control, limited resource throttling

None provide hierarchical grouping, accounting, or delegation. This is a fundamental limitation for container runtime development on macOS.

9. taskpolicy and QoS Classes

taskpolicy Command

The most powerful per-process resource control tool on macOS. Wraps setiopolicy_np(3) and setpriority(2):

FlagEffect
-bBackground priority (PRIO_DARWIN_BG) -- throttles CPU scheduling, disk I/O, network I/O. On Apple Silicon: confines to E-cores.
-BRemove background priority
-c clampQoS clamp: utility, background, or maintenance
-d policyDisk I/O policy: default, throttle, etc.
-m limitMemory limit in MiB (sets Jetsam high-water mark)
-j priJetsam priority level (0-21; lower = killed first)
-P pcontrolResource exhaustion action: kill, throttle, suspend
-t / -lThroughput / latency tier
-p pidTarget an existing process
Can taskpolicy limit CPU to a percentage?

No. It can demote a process to background QoS (E-cores only on Apple Silicon) or apply a QoS clamp, but it cannot set a precise CPU percentage cap. It is a "brake, not an accelerator."

QoS Classes

QoS ValueNameApple Silicon Behavior
33userInteractiveP-cores preferred, highest priority
25userInitiatedP-cores preferred
17utilityMay run on E-cores
9backgroundE-cores only -- ~12-23% of full chip performance

On Apple Silicon with a base chip (4E + 4P), taskpolicy -b confines a process to E-cores, effectively limiting it to ~12-23% of full-chip performance. This is the closest macOS has to a CPU cap.

I/O Throttle Tiers

Via setiopolicy_np: IOPOL_IMPORTANT > IOPOL_STANDARD > IOPOL_UTILITY > IOPOL_THROTTLE > IOPOL_PASSIVE. The XNU kernel maps these to internal THROTTLE_LEVEL_TIER0 through TIER3.

10. Jetsam / memorystatus

Jetsam is the kernel subsystem that actually enforces memory limits on macOS (and iOS). It is far more effective than RLIMIT_RSS.

How It Works

  1. Maintains 21+ priority bands (linked-list buckets, lowest to highest priority)
  2. Monitors phys_footprint ledger per process (includes RSS, compressed memory, IOKit allocations)
  3. Under memory pressure, kills processes from lowest to highest priority band
  4. Processes can have a High Water Mark -- exceeding it makes them eligible for immediate termination

Kill Algorithm

  1. Start at lowest non-empty priority bucket (IDLE_HEAD at -2)
  2. Kill first process in that bucket; check if enough memory freed
  3. If not, continue through bucket, then move to next higher bucket
  4. If normal kills are insufficient, aggressive mode kills multiple candidates across bands simultaneously

Before killing, NOTE_VM_PRESSURE is sent via kevent. Processes can respond via DISPATCH_SOURCE_TYPE_MEMORYPRESSURE. The public API os_proc_available_memory() returns bytes available before jetsam.

Documentation Status

The XNU source code is open (headers + implementation), and Apple documents jetsam event reports. But the memorystatus_control() syscall itself is undocumented SPI -- learned from reading kernel source or community research (notably Jonathan Levin's newosxbook.com).

11. proc_set_dirty / proc_set_cpumon_params

proc_set_cpumon_params -- CPU Usage Monitoring

This function is part of macOS's libproc private API. It configures CPU usage monitoring (not capping).

int proc_set_cpumon_params(pid_t pid, int percentage, int interval);

Implementation uses __process_policy(PROC_POLICY_SCOPE_PROCESS, PROC_POLICY_ACTION_SET, PROC_POLICY_RESOURCE_USAGE, PROC_POLICY_RUSAGE_CPU, ...).

Monitor, Not Limiter

This sets a CPU usage monitor, not a hard cap. It watches whether a process exceeds a given percentage over a given interval (seconds). When exceeded, a Mach exception notification is sent. It does not throttle CPU usage.

Default values: 50% over 180 seconds (3 minutes).

12. IOKit Resource Management

IOKit is Apple's device driver framework. It provides memory descriptor management (IOMemoryDescriptor) for DMA transfers and device-interface mechanisms for userspace driver access.

Not a Resource Management API

IOKit does not provide per-process resource limiting. The only "resource" aspect is that Jetsam includes IOKit memory allocations in its phys_footprint accounting, so IOKit memory usage counts against a process's jetsam memory limit.

For Container Runtime Development

The most useful primitives for a macOS container runtime are:

  • Memory limiting: taskpolicy -m <MiB> or memorystatus_control(SET_JETSAM_TASK_LIMIT, ...) for hard limits
  • CPU scheduling: taskpolicy -b or -c background for background demotion; RLIMIT_CPU for total CPU time caps
  • I/O throttling: taskpolicy -d throttle or setiopolicy_np()
  • File descriptors: setrlimit(RLIMIT_NOFILE, ...)
  • The absence of cgroups means there is no way to limit a group of processes collectively. Each process must be limited individually.

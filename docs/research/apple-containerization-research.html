1. Overview and History

Apple announced the Containerization framework and the container CLI at WWDC 2025 (June 2025). It is an open-source (Apache 2.0) Swift package that enables running Linux containers on macOS using Virtualization.framework on Apple Silicon. At WWDC 2026, Apple shipped version 1.0.0 with the addition of Container Machines (persistent Linux VM environments) and full macOS 26 support.

Two repositories:
  • apple/containerization -- The Swift framework/library (APIs for images, VMs, networking, ext4, vminitd)
  • apple/container -- The CLI tool and system services (apiserver, vmnet daemon, image store, runtime)

3. Isolation Model (VM-per-Container)

Core design: Every container runs inside its own lightweight Linux VM. This is NOT namespace-based isolation. Each container gets its own Linux kernel, providing hypervisor-level (hardware-backed) isolation.

This is architecturally equivalent to what Kata Containers does on Linux, but reimplemented from scratch in Swift for Apple Silicon. As one analyst put it: Apple "basically wrote Kata for macOS in Swift."

Two Container Models

TypeClassVM ModelUse Case
LinuxContainerLinuxContainer1 VM per containerMaximum isolation (default)
LinuxPodLinuxPod1 VM, multiple containersShared resources, k8s-style pods

LinuxContainer Lifecycle

  1. create() -- Initializes VM, boots kernel, waits for vminitd on vsock:1024, mounts filesystems, configures networking
  2. start() -- Launches the container's initial process inside the VM
  3. exec() -- Runs additional processes (like docker exec)
  4. stop() -- Gracefully shuts down VM and frees resources

LinuxContainer Defaults

CPUs:   4
Memory: 1024 MiB (1 GiB)

Boot Sequence (from source)

  1. Validate VM is in stopped state
  2. Prestart hook: install Rosetta binary translation if requested
  3. Kernel boot via VZVirtualMachine.start()
  4. Agent handshake: block until vsock port 1024 (vminitd) responds
  5. Feature configuration: enable Rosetta post-boot if needed
  6. Time sync: initiate periodic host-guest clock synchronization

Source: DeepWiki VM Management, LinuxContainer.swift

4. vminitd -- The Guest Init System

vminitd is a minimal init system written in Swift, cross-compiled from macOS using the Swift Static Linux SDK with musl libc. It runs as PID 1 inside each VM and provides a gRPC API over vsock (port 1024).

gRPC Service API (from SandboxContext.proto)

The full gRPC service definition covers these categories:

CategoryOperations
FilesystemMount, Umount, Mkdir, WriteFile, Copy (bidirectional via vsock), Stat, FilesystemOperation (trim/freeze/thaw)
ProcessCreateProcess, StartProcess, KillProcess, WaitProcess, DeleteProcess, ResizeProcess (TTY), CloseProcessStdin
NetworkIpLinkSet, IpAddrAdd, IpRouteAddLink, IpRouteAddDefault, ConfigureDns, ConfigureHosts
EnvironmentSetenv, Getenv, Sysctl, SetTime, SetupEmulator (binfmt for Rosetta)
StatisticsContainerStatistics (process, memory, CPU, block I/O, network, memory events)
Vsock ProxyProxyVsock (bridge vsock to unix sockets), StopVsockProxy

The Minimal Filesystem

The VM's root filesystem contains only the vminitd binary. No core utilities (ls, cp, cat), no dynamic libraries, no libc. This drastically reduces attack surface.

I/O Streams via Vsock

Each container process gets dedicated vsock ports for stdin, stdout, stderr. Port allocation uses atomic counters starting at 0x1000_0000.

Source: SandboxContext.proto, Vminitd.swift

5. Filesystem Handling

Primary: EXT4 Block Devices

Container filesystems are exposed as EXT4-formatted block devices via virtio-blk. The ContainerizationEXT4 module is an entire ext4 filesystem implementation written in Swift that can format, create directory structures, and populate filesystems directly -- no external tools needed.

The kernel command line for ext4 rootfs: console=hvc0 init=/sbin/vminitd ro rootfstype=ext4 root=/dev/vda

proc      /proc

cgroup2   /sys/fs/cgroup

Block Device Features

  • Disk image caching modes: automatic, cached, uncached
  • Synchronization modes: full, fsync, none
  • Network Block Device (NBD) support: nbd://, nbds://, nbd+unix:// schemes
  • Copy-on-write cloning mentioned for macOS-specific file copying

Does It Use APFS Clones?

Indirect The framework itself does not explicitly call APFS clone APIs (like clonefile()). However, the Mount.swift source mentions "copy-on-write cloning" for macOS-specific file copying. Since the host filesystem is APFS, any file copies done on the host side will inherently use APFS clonefile semantics. The primary isolation mechanism is the per-VM ext4 block device, not APFS volume clones.

Performance Note

The pure-Swift ext4 implementation has known performance concerns. Anil Madhavapeddy reported that unpacking a 415.9 MB image with 112,000+ entries took approximately 9+ minutes on an M4 MacBook Air.

Sources: Mount.swift, AttachedFilesystem.swift, Anil Madhavapeddy analysis

6. Networking

Architecture

Every container gets a dedicated IP address -- no port mapping needed. Networking is provided by the vmnet.framework on the host side and configured via netlink (gRPC calls to vminitd) on the guest side.

Host-Side: VmnetNetwork

  • Default mode: VMNET_SHARED_MODE (NAT)
  • DHCP is explicitly disabled (vmnet_network_configuration_disable_dhcp)
  • Static IP allocation via the Allocator struct
  • IPv4 pool: addresses between cidrV4.lower + 2 and cidrV4.upper - 3 (rotating)
  • IPv6: UInt32 index applied to host portion of prefix
  • Dual-stack (IPv4 + IPv6) support
  • Configurable MTU (default 1500)
  • Per-container MAC address assignment

Guest-Side: Network Configuration via gRPC

  1. IpLinkSet -- bring interface up, set MTU
  2. IpAddrAdd -- assign IPv4/IPv6 addresses
  3. IpRouteAddDefault -- set default gateway (first interface)
  4. ConfigureDns -- write resolver configuration
  5. ConfigureHosts -- write /etc/hosts

NATInterface

The NATInterface struct configures: IPv4 CIDR + optional gateway, IPv6 CIDR + optional gateway, MAC address, MTU.

DNS

The container CLI tool includes an embedded DNS service. Containers can be accessed by domain names (e.g., myapp.test). Setting up the DNS service requires administrator privileges.

7. Resource Management and Limits

VM-Level Resources

ResourceDefaultConfigurable
CPUs4Yes, per container
Memory1 GiBYes, per container (in bytes)
Network interfaces[]Yes, array of Interface objects
Nested virtualizationfalseYes (requires hardware support)

Guest-Level Resources (cgroups v2)

Inside LinuxPod, per-container resource limits are enforced via cgroups v2:

  • CPU limits (can oversubscribe beyond pod total)
  • Memory limits with swap control
  • Per-container namespaces: mount, UTS, cgroup, IPC
  • Optional shared PID namespace (via pause container)

Statistics Tracked (from ContainerStatistics.swift)

  • Process: current count, limit
  • Memory: usage, limit, swap usage, swap limit, cache, kernel stack, page faults, reclamation stats
  • CPU: total usage (microseconds), user time, system time, throttling periods/duration
  • Block I/O: per-device read/write bytes and operations (by major:minor)
  • Network: per-interface packets/bytes/errors (rx/tx)
  • Memory Events: low reclamation, high-limit exceeded, max-limit hits, OOM triggers, OOM kills
Key insight: Resources are dynamically allocated -- CPU and memory are only consumed when containers are running. When idle, resources are released back to the host. This is a property of Virtualization.framework's balloon/yield behavior.

Sources: ContainerStatistics.swift, VMConfiguration.swift

8. Security Model

Isolation Layers

  1. Hypervisor isolation -- Each container has its own Linux kernel in a separate VM. No shared kernel means no container escape via kernel exploits.
  2. Minimal attack surface -- The VM root filesystem contains ONLY the vminitd binary. No shell, no utilities, no libc, no dynamic libraries.
  3. Scoped file sharing -- Directories are shared on a per-container basis only. A container cannot access files shared with other containers.
  4. Process isolation -- Processes in one container cannot observe processes on the host or in other containers.

Does It Use Sandbox Profiles (.sb files)?

No Apple's containerization does NOT use macOS sandbox profiles (.sb files / Seatbelt / TrustedBSD MAC). The isolation is entirely at the hypervisor level via Virtualization.framework. In fact, issue #737 explicitly asks whether Apple Containerization will ever offer native process sandboxing without requiring Linux VMs -- the answer is currently no. The SandboxContext in the source code is the name of the gRPC protobuf service for the vminitd agent, NOT a macOS sandbox profile.

Required Entitlements

  • com.apple.security.virtualization -- Required for Virtualization.framework
  • com.apple.vm.networking -- Required for vmnet.framework

Sources: Issue #737, WWDC25 Session

9. Kernel Requirements

  • Minimum version: Linux 6.14.9+ (tested), 6.12.28 also used in practice
  • Default source: Kata Containers project provides pre-built kernels
  • Critical requirement: VIRTIO drivers must be compiled into the kernel (not as modules)
  • Architecture: arm64 only (x86_64 via Rosetta 2 translation)
  • Custom config: Available at kernel/config-arm64 in the repo
  • Optimized for: Sub-second boot with minimal driver set targeting container workloads

Required Kernel Features (VIRTIO)

  • virtio-blk -- Block device storage (ext4 rootfs)
  • virtio-net -- Network interfaces
  • virtio-fs -- Shared directory filesystem
  • virtio-vsock -- Host-guest communication channel
  • virtio-console -- Serial console (hvc0)
  • cgroup2 -- Resource management (for LinuxPod)
  • ext4 -- Root filesystem
  • Linux namespaces -- mount, UTS, cgroup, IPC, PID (for pod containers)

Rosetta 2 Support

For running x86_64 containers on arm64: Rosetta is installed as a VZLinuxRosettaDirectoryShare virtiofs device, with binfmt_misc configured via the SetupEmulator gRPC call. Known issue with kernel 6.13 builds.

Sources: Repository README, DeepWiki VM Management

10. Undocumented / Private APIs

Mostly public APIs Based on thorough source code analysis, the framework primarily uses documented public APIs:
  • Virtualization.framework -- All public API (VZVirtualMachine, VZLinuxBootLoader, VZVirtioBlockDeviceConfiguration, etc.)
  • vmnet.framework -- This is a semi-documented C framework. It was originally reverse-engineered for OCaml/MirageOS around 2014. Apple has since made it more accessible but it remains lower-level than Virtualization.framework.
  • CShim target -- The Package.swift includes a C shim target, likely for bridging to C APIs not directly accessible from Swift (potentially vmnet C functions).

No evidence of private SPI (System Programming Interfaces) or undocumented kernel extensions was found in the source code.

Source: Anil Madhavapeddy analysis (notes vmnet was reverse-engineered circa 2014)

11. LinuxPod (Multi-Container VMs)

LinuxPod is marked as experimental. It runs multiple containers in a single VM, similar to Kubernetes pods.

Key Differences from LinuxContainer

FeatureLinuxContainerLinuxPod
VM per containerYesNo -- shared VM
Kernel isolationFullShared kernel, namespace isolation
NetworkingDedicated per VMShared within pod
Resource limitsVM-levelcgroups v2 per container
Hot-pluggingN/AYes -- add containers to running VM
Shared volumesNoYes -- NBD-backed, mountable by multiple containers

Pod Namespace Configuration

  • Each container: dedicated mount, UTS, cgroup, IPC namespaces
  • PID namespace: shared (via pause container) or isolated
  • Container rootfs at: /run/container/{id}/rootfs
  • Shared volumes at: /run/volumes/{name}

Source: LinuxPod.swift

12. Container Machines (WWDC26)

New in v1.0.0 (June 2026): Container Machines are persistent, long-lived Linux environments built on Containerization. They combine container speed with VM persistence -- like WSL for macOS.

Key Properties

  • Persistent: Modifications survive across stop/start cycles
  • Ext4 root filesystem for persistent storage
  • Automatic user mapping: macOS username is mirrored inside the VM
  • Automatic directory sharing: CWD is mirrored via virtiofs
  • Sub-second start times
  • Isolated networking with dedicated IP per machine
  • OCI image base: Created from standard container images

Source: WWDC26 Session: Discover Container Machines

15. Direct Answers to Your Questions

Is each container a lightweight VM?

Yes

Each LinuxContainer runs in its own Virtualization.framework VM with a dedicated Linux kernel. LinuxPod shares one VM across multiple containers with namespace isolation.

Does it use sandbox profiles (.sb)?

No

No macOS sandbox profiles or Seatbelt policies. Isolation is purely via the hypervisor. The "SandboxContext" in source is a gRPC service name, not a macOS sandbox.

Does it use APFS clones?

Not directly

The framework creates ext4 block device images per container. Standard macOS file copy on APFS will use clonefile automatically, but there is no explicit APFS clone API usage for isolation.

How does networking isolation work?

Per-VM network stack

Each VM gets a dedicated vmnet interface with static IP allocation (DHCP disabled). Guest networking configured via gRPC/netlink calls. Full network stack isolation.

Does it use undocumented APIs?

Minimal

Primarily public Virtualization.framework APIs. vmnet.framework is semi-documented (lower-level C API). A CShim bridges some C functions. No evidence of private SPI.

Resource limiting beyond Virt.framework?

Yes (in pods)

LinuxPod uses cgroups v2 for per-container CPU/memory limits within a shared VM. LinuxContainer relies on VM-level allocation (Virtualization.framework). Statistics include OOM events, throttling, and per-device I/O.

What kernel features does it rely on?

Standard Linux

VIRTIO (blk, net, fs, vsock, console), ext4, cgroups v2, Linux namespaces (mount, UTS, cgroup, IPC, PID), netlink, binfmt_misc (Rosetta). No custom kernel modules.
